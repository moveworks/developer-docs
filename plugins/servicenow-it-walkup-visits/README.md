# Description

Gives employees a conversational front door to ServiceNow's Walk-Up Experience: book a Tech
Lounge appointment (in-person, remote, or a location's choice of either), check in to a location's
walk-in queue and get a real queue position, or view/cancel an existing appointment or queue entry
— all without leaving chat. Unlike a pure lookup plugin, this one writes: it creates and cancels
real `wu_appointment` and `interaction` records, so it includes a duplicate-booking check (offers
to cancel and rebook rather than silently creating a second booking) and captures a reason-for-visit
onto the resulting record.

# Pre-requisites

Before installing and using the **IT Walk-up Visits** plugin, please ensure the following
requirements are met:

## 1. Employee Slate for ITSM + ServiceNow Walk-Up Experience

This plugin requires **Employee Slate for ITSM** (`sn_itsm_empworks`) **v2.0.3 or later** (the
September 2026 release) — this app ships the custom `walk_in/*` Scripted REST API the plugin
depends on for check-in, cancellation, and read lookups (see Implementation Details below).

Employee Slate for ITSM in turn requires ServiceNow's **Walk-Up Experience** plugin (`com.snc.walkup`)
to be active on the same instance — it provides the `wu_location_queue` / `wu_appointment` /
`wu_m2m_location_queue_reason` tables and the `sn_walkup.WalkUpAPI` script include this plugin's
routes call directly for check-in. **This is a soft dependency, not a platform-enforced one:**
Employee Slate for ITSM's `plugin.xml` has no hard `<requires>` entry for `com.snc.walkup` — its
walk-up-specific records live under a conditional-install path (`src/fluent/if/com.snc.walkup/`)
that only activates when Walk-Up Experience happens to be present. Installing Employee Slate for
ITSM without it will not fail, but the walk-up records this plugin needs simply won't be there, so
confirm Walk-Up Experience is active **before** installing Employee Slate for ITSM, not after. See
ServiceNow's [**Walk-up Experience**](https://www.servicenow.com/docs/r/it-service-management/walk-up-experience/walkup-experience-landing-page.html)
documentation.

Also required:

- **Appointment Booking** (`sn_apptmnt_booking`) — for appointment-slot availability lookups.
- **Service Catalog**, with a configured Tech Lounge booking catalog item — bookings are submitted
  through that item's `submit_producer` endpoint, not a raw table write.

## 2. User Identity Resolution

Unlike plugins that resolve the acting employee via Moveworks' per-user identity dot-walk
(`meta_info.user.external_system_identities.<source>.external_id`, only populated under User
Consent Auth), this plugin resolves the requester's ServiceNow `sys_user` sys_id explicitly, once,
early in the conversation, via a `sys_user` lookup by email — then threads that sys_id through as
`userId` on every subsequent `walk_in/*` call. This is a deliberate consequence of using Service
Account auth (see below), not an oversight: there is no per-user OAuth identity to dot-walk under a
shared service account, so identity has to be resolved and carried explicitly instead.

## 3. ServiceNow Connector

This plugin uses **Service Account authentication** (OAuth 2.0 Client Credentials grant) — a
single shared connector identity, not per-employee User Consent Auth (UCA). This was discussed and
confirmed with Steve Rankich during architecture review: the target user for every action here is
the requester, who typically has no direct ACL access to the `wu_*`/`interaction` tables this
plugin reads and writes, so the lookup and write calls run under a dedicated service account
instead. Because every `walk_in/*` route executes under that shared identity rather than the real
employee's own session, **the connector cannot rely on session identity for ownership checks** —
every route requires the real employee's `sys_user` sys_id passed explicitly as `userId` in the
request body (see User Identity Resolution above). Scope the service account to read access on
`wu_location_queue`, `wu_m2m_location_queue_reason`, `interaction`, and `sys_user`, plus write
access on `wu_appointment` and `interaction` for the booking/check-in/cancel paths.

If you have not already configured the connector, follow the
[**OAuth 2.0 Client Credentials guide**](https://marketplace.moveworks.com/connectors/servicenow#oauth-2-0-client-credentials).
The connector must be fully set up before installing this plugin. Once configured, follow the
[**plugin installation documentation**](https://help.moveworks.com/docs/ai-agent-marketplace-installation)
for detailed steps on how to install and activate the plugin in **Agent Studio**.

# How This Plugin Works

The process routes on a single `book_or_queue` slot with two explicit values — `book` and
`manage` — plus an untyped fallback that handles walk-in check-in. Each of the three resulting
flows runs its own duplicate-booking check independently; **neither cross-checks the other
table** — booking only looks for an existing appointment, walk-in only looks for an existing queue
entry.

- **Book an appointment.** First checks whether the employee already has an active **appointment**
  — if so, offers to cancel it before continuing (see "Book again" below). Then resolves the
  location's supported contact type(s) — in-person only, remote only, or a choice of both — checks
  slot availability (with a "no slots in the next two weeks" fallback), collects a reason, and
  submits through the Tech Lounge catalog item's `submit_producer` endpoint behind a native
  confirmation gate.
- **Join the walk-in queue** (the fallback case — not an explicit slot value). First checks whether
  the employee already has an active **queue entry** — if so, offers to cancel it. Then checks
  whether the location is remote-only, since walk-in isn't offered there. If the employee is
  redirected to booking instead (location ineligible, or they decline to walk in), the process
  **re-enters the entire book flow from its own duplicate-check onward** — a full re-entry, not a
  shortcut. Otherwise it checks the employee in via `/checkin` (behind a native confirmation gate)
  and reports a real queue position.
- **View / manage.** Looks up both the employee's active appointment and queue entry together. If
  both exist, asks which to cancel; if only one exists, offers to cancel that one. Cancelling either
  flips the underlying `interaction` to `closed_abandoned` rather than deleting anything, gated by a
  conversational "would you like to cancel it?" (`confirm_cancel`/`manage_cancel_choice`) rather than
  the native confirmation gate.

**"Book again" after a cancel.** Every appointment-context cancel (booking's own duplicate-check,
and manage's appointment-only or both-active paths) offers to book a new appointment afterward and,
if accepted, re-runs the full slot-collection flow. This is **not symmetric** — cancelling a
queue-only entry never offers to book again.

# Implementation Details

**Note:** References to the instance must be updated after the plugin is installed.

## API Details

### Custom REST API — `walk_in` service (ships with this plugin's app, `sn_itsm_empworks`)

All routes are `POST`, JSON in/out, and always return HTTP 200 — success/failure is signaled via a
field in the body (e.g. `checkedIn`, `cancelled`), not the status code. Every route requires the
real employee's `sys_user` sys_id passed explicitly, since the routes run under a shared connector
identity and cannot use session-based ACL checks (see Pre-requisites above).

| Route | Purpose | Request body |
|---|---|---|
| `/checkin` | Check the employee into a location's walk-in queue. | `{"locationId":"<wu_location_queue sys_id>","userId":"<sys_user sys_id>","reasonId":"<wu_reason sys_id>","reasonText":"optional detail"}` |
| `/cancel` | Cancel a walk-in queue entry or appointment (closes the underlying `interaction`). | `{"interactionSysId":"<interaction sys_id>","userId":"<sys_user sys_id>"}` |
| `/locations` | List active Tech Lounge locations with schedule/contact-type fields. | `{}` |
| `/active-queue` | Look up the employee's own active walk-in queue entry, if any. | `{"userId":"<sys_user sys_id>"}` |
| `/queue-count` | Count active queue entries ahead of a given time, to compute position. | `{"cmnLocationId":"<cmn_location sys_id>","openedAt":"<timestamp>"}` |
| `/active-appointment` | Look up the employee's own active/upcoming appointment, if any. | `{"userId":"<sys_user sys_id>","nowUtc":"<timestamp>"}` |
| `/appointment-state` | Recheck a single appointment's state after a write, to confirm it landed. | `{"appointmentSysId":"<wu_appointment sys_id>","userId":"<sys_user sys_id>"}` |

**`/cancel` confirmed as a single shared route.** The live process wraps it in two different
compound actions — one for cancelling an appointment, one for a queue entry — but both call this
exact same `/cancel` route under the hood. The only difference: the appointment variant makes one
extra call afterward to `/appointment-state`, re-reading the appointment to confirm the cancel's
side-effect (the "Cancel Appointments on Close Abandon" business rule) actually landed on
`wu_appointment`; the queue variant has no equivalent recheck.

**Manage's existing-booking lookup isn't a separate endpoint.** It's a compound action that simply
runs `/active-appointment`'s and the queue-check's underlying HTTP actions in parallel — no new
route, no new table access beyond what's already listed above.

**Remote-only eligibility check uses the raw Table API, not `/locations`.** Before offering
walk-in, the process calls `GET /api/now/table/wu_location_queue` directly — `sysparm_query=active=true`,
`sysparm_fields=sys_id,name,schedule,appointment_booking,location,appointment_booking.catalog_item,contact_types_for_appointment`,
`sysparm_display_value=all`, `sysparm_limit=50` — rather than the custom `/locations` bypass route.
This means `contact_types_for_appointment` is read through the real field-level wildcard ACL, which
is why the service account needs `sn_walkup.walkup_technician` (or `walkup_manager`/`awa_manager`)
for this call to return that field at all — not just for `wu_appointment` access as documented
under Pre-requisites.

Example — check-in:

```bash
curl --location 'https://<YOUR_INSTANCE>/api/sn_itsm_empworks/walk_in/checkin' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data '{"locationId":"<wu_location_queue sys_id>","userId":"<sys_user sys_id>","reasonId":"<wu_reason sys_id>"}'
```

Example — cancel:

```bash
curl --location 'https://<YOUR_INSTANCE>/api/sn_itsm_empworks/walk_in/cancel' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data '{"interactionSysId":"<interaction sys_id>","userId":"<sys_user sys_id>"}'
```

**Confirmation behavior:** verified directly against the live process
(`Walkup_Process_v34_QueueCountCentralized`). Check-in runs behind Moveworks' native confirmation
gate (`needs_confirmation: true`) — the user sees a confirm step before the `/checkin` call fires.
Cancel is the opposite: the `/cancel` call itself runs with `needs_confirmation: false`, and is
gated instead by a manual conversational confirmation — the process asks "Would you like to cancel
it?", captures the answer in a `confirm_cancel` slot, and only calls `/cancel` if
`confirm_cancel.value == "yes"`. This same pattern (ask, capture in `confirm_cancel`, branch) is
reused across every cancel path — the duplicate-booking offer, a direct appointment cancel, and a
direct queue-entry cancel all use it.

**Key nuances:**

- **No HTTP-status-based error signaling.** Always check the body's own success field
  (`checkedIn` / `cancelled`) plus an `error` code (`INVALID_PARAMETERS`, `LOCATION_NOT_FOUND`,
  `ALREADY_QUEUED`, `LOCATION_CLOSED`, `FORBIDDEN`, `NOT_FOUND`, `INTERNAL_ERROR`) rather than the
  HTTP status alone.
- **Explicit ownership checks replace session-based ACLs.** `/cancel` and the state-lookup routes
  verify the passed `userId` against the record's `contact`/`opened_for` field themselves — omitting
  or mismatching `userId` will not silently succeed.
- **Cancel is non-destructive.** It flips `interaction.state` to `closed_abandoned`; it does not
  delete the interaction, appointment, or queue record.

### Standard ServiceNow APIs

- **Table API reads** — `wu_location_queue`, `wu_m2m_location_queue_reason` (reason-for-visit
  picklist), `interaction`, and `sys_user` (resolving the requester's `sys_id` by email).
- **Appointment availability** — `GET /api/sn_apptmnt_booking/appointment/availability`, to check
  open slots before booking.
- **Catalog producer submit** — `POST /api/sn_sc/servicecatalog/items/{catalog_id}/submit_producer`,
  the actual booking write path; creates the `wu_appointment` and its linked `interaction`.
  **Confirmation behavior:** verified against the live process — booking runs the duplicate-check
  described above first, and the final submission itself also runs behind Moveworks' native
  confirmation gate (`needs_confirmation: true`), same as check-in.

# What Is In Scope for This Plugin?

- Booking a Tech Lounge appointment at in-person-only, remote-only, or either-type locations,
  resolving or prompting for contact type as needed.
- Detecting an existing appointment before starting a new booking, and (independently) an existing
  queue entry before joining the walk-in queue — each check is scoped to its own flow, not
  cross-checked against the other table.
- Offering to book a new appointment after cancelling one in an appointment context (booking's own
  duplicate-check, or either path through Manage) — not offered after cancelling a queue-only entry.
- Redirecting a walk-in request into the full booking flow when the location is remote-only or the
  employee declines to walk in.
- Telling the employee when no appointment slots are available in the next two weeks.
- Joining a location's walk-in queue and reporting a real queue position.
- Viewing an employee's existing appointment and/or walk-in queue entry together, and letting them
  choose which to cancel when both exist.
- Cancelling an existing appointment or walk-in queue entry.
- Capturing a reason-for-visit (category + free-text detail) onto the resulting appointment and
  its linked interaction.

# What Is Out of Scope for This Plugin?

- Rescheduling an existing appointment to a new time or location (only cancel-then-rebook is
  supported, not an in-place reschedule).
- Offering walk-in queue join for remote-only locations (booking is available there; walk-in is
  not).
- Creating, editing, or deactivating Tech Lounge locations, schedules, or reason-for-visit
  categories — these are admin-configured data, not something this plugin manages.
- Estimating overall queue load or wait time across all locations.
- Acting on behalf of another employee.
- Proactively notifying an employee (e.g., "you're next") outside of a direct request.
