# Introduction

Frontline retail store employees can report broken in-store equipment — scanners, printers, registers, and more — right from the Moveworks AI Assistant, without navigating the ServiceNow RSM portal, filling out a form, or calling the help desk. The store is auto-detected from the employee's membership, an optional photo can be attached, and the plugin blocks duplicate cases before a second ticket is ever opened for the same device.

For store operations and facilities teams, this means faster reporting of equipment issues, less store downtime, and a cleaner case queue free of duplicate tickets — turning a multi-step portal task into a few seconds of conversation.

# Pre-requisites

Before installing and using the **Create Break-Fix Case** plugin, please ensure the following requirements are met:

## **1. ServiceNow Retail Store Services Application**

This plugin operates on the **Retail Store Services** break-fix case table (`sn_rtl_stre_servcs_bf_case`) and its supporting CSM tables (`sn_csm_service_organization_member`, `sn_install_base_item`). The **Retail Store Services** application must be installed and active on your ServiceNow instance before installing this plugin.

Install it from the ServiceNow Store: [**Retail Store Services**](https://store.servicenow.com/store/app/f84516ce1b87e210c43e65b2604bcb7a)

## **2. ServiceNow Connectors**

This plugin uses **two** ServiceNow connectors side by side:

**Connector 1 — OAuth 2.0 Authorization Code (user-based / User Consent auth).** Used for every call in this plugin *except* case creation itself: the store lookup, device lookup, duplicate check, and the optional attachment upload all execute under the **authenticated user's own ServiceNow identity**, respecting each user's existing ServiceNow roles and ACLs. Set this up following the [**OAuth 2.0 Authorization Code guide**](https://marketplace.moveworks.com/connectors/servicenow#oauth-2-0-authorization-code).

**Connector 2 — OAuth 2.0 Client Credentials (non-user / service account).** Used **only** for the case-creation POST. This call runs under a **dedicated service account**, scoped to a role limited to retail break-fix operations only (no standing access beyond what this plugin needs). Set this up following the [**OAuth 2.0 Client Credentials guide**](https://marketplace.moveworks.com/connectors/servicenow#oauth-2-0-with-client-credentials).

Both connectors must be fully set up before installing this plugin.

Once configured, follow our [**plugin installation documentation**](https://help.moveworks.com/docs/ai-agent-marketplace-installation) for detailed steps on how to install and activate the plugin in **Agent Studio**.

# **How This Plugin Works**

The plugin identifies the user's store automatically from their store membership, asking them to pick only if they belong to more than one. It then has the user choose the affected device, describe the issue, set a priority, and optionally attach a photo. Before creating the case, it checks for an existing open case on that device (treating a Resolved-but-not-Closed case as a duplicate too) and returns the existing case instead of opening a second one. The user reviews a summary — store, device, issue, priority, and attachment — and confirms before anything is created.

# **Implementation Details**

## API Details

All calls run against the customer's ServiceNow instance. Replace `<YOUR_INSTANCE>` with your ServiceNow instance hostname and `<ACCESS_TOKEN>` with the access token for the connector noted on each call — the authenticated user's OAuth token (Connector 1) for every call except case creation, and the service account's Client Credentials token (Connector 2) for the create call only.

### **API #1: Resolve the User's Store(s)** *(Connector 1 — user-based)*

Returns the service-organization membership rows for the requesting user. When exactly one row is returned, the store slot fills silently; otherwise the user picks.

```bash
curl --location 'https://<YOUR_INSTANCE>/api/now/table/sn_csm_service_organization_member?sysparm_query=user.email=<USER_EMAIL>&sysparm_display_value=true' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Accept: application/json'
```

**Parameters:**

- `USER_EMAIL` *(string):* The requesting user's email (`meta_info.user.email_addr`).

### **API #2: Resolve Install-Base Items for the Store** *(Connector 1 — user-based)*

Returns the devices/equipment registered to the resolved store, scoped by the store reference.

```bash
curl --location 'https://<YOUR_INSTANCE>/api/now/table/sn_install_base_item?sysparm_query=<STORE_SCOPE_QUERY>&sysparm_display_value=true' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Accept: application/json'
```

**Parameters:**

- `STORE_SCOPE_QUERY` *(string):* Encoded query scoping install-base items to the resolved store.

### **API #3: Duplicate-Case Check** *(Connector 1 — user-based)*

Checks for an open break-fix case on the chosen `install_base` item. Excludes terminal states (Closed = `3`, Cancelled = `7`). Limited to 1 result.

```bash
curl --location 'https://<YOUR_INSTANCE>/api/now/table/sn_rtl_stre_servcs_bf_case?sysparm_query=install_base=<INSTALL_BASE_SYS_ID>^stateNOT IN3,7&sysparm_limit=1&sysparm_display_value=true' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Accept: application/json'
```

**Parameters:**

- `INSTALL_BASE_SYS_ID` *(string):* `sys_id` of the chosen install-base item.

**Key nuances:**

- If this call returns a row, the plugin returns the existing case and never runs the create POST.

### **API #4: Create the Break-Fix Case** *(Connector 2 — service account)*

Creates the case on `sn_rtl_stre_servcs_bf_case`. This is the **only** call in the plugin that runs under the service-account connector rather than the requesting user's own session. `contact_type` is set to `moveworks` so the source of creation is auditable.

```bash
curl --location 'https://<YOUR_INSTANCE>/api/now/table/sn_rtl_stre_servcs_bf_case' \
  --request POST \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data '{
    "short_description": "{{short_description}}",
    "description": "{{description}}",
    "install_base": "{{install_base_sys_id}}",
    "requesting_service_organization": "{{store_sys_id}}",
    "priority": "{{priority}}",
    "opened_by": "{{requesting_user_sys_id}}",
    "contact_type": "moveworks"
  }'
```

**Parameters:**

- `priority` *(string, optional):* `1` (Critical), `2` (High), `3` (Moderate), `4` (Low). Omit to fall back to ServiceNow's default priority calculation.
- `opened_by` *(string, required):* Must be explicitly set to the requesting user's sys_id. Because this call runs under the service-account connector, there is no user session for ServiceNow to infer it from — omitting it would attribute the case to the service account instead of the actual requester.

### **API #5: Upload Attachment (Optional)** *(Connector 1 — user-based)*

Attaches the user's file to the created case. If this call fails, the case is preserved and `attachment_warning` is surfaced — the attachment failure does **not** roll back the case.

```bash
curl --location 'https://<YOUR_INSTANCE>/api/now/attachment/upload' \
  --request POST \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: multipart/form-data' \
  --form 'table_name=sn_rtl_stre_servcs_bf_case' \
  --form 'table_sys_id={{case_sys_id}}' \
  --form 'uploadFile=@{{file}}'
```

# **What Is In Scope for This Plugin?**

- Submitting new break-fix cases for in-store equipment.
- Auto-resolving the user's store (prompting when they belong to more than one).
- Capturing store, device, priority, a short and long description, and an optional attachment.
- Detecting and blocking duplicate cases for the same device when an open (non-terminal) case already exists.

# **What Is Out of Scope for This Plugin?**

- Tracking, viewing, or updating existing break-fix cases (handled by **Get Break-Fix Case Details** and **Update Break-Fix Case**).
- Fulfillment, assignment, or resolution of cases.
- Adding comments, extending due dates, or reassigning fulfillers on existing cases.
- Bulk creation of multiple break-fix cases in a single utterance.
- Opening a case on behalf of another user (the case is always opened by the requesting user).
